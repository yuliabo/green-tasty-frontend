**Проєкт:** `frontend/restaurant-frontend-app`
**Сторінка:** `http://localhost:4200/reservations/demo-reservation/group-order?demo`
**Статус:** Практичне + Рівні 1–3 готові (`npm run test:hw` — 61/61 GREEN).

### Рівень 2 — живі дані, стани, Submit (усього 52 тести: 26 helpers + 8 картка + 5 сервіс + 13 сторінка)

- **`GroupOrdersService`** (`src/app/services/group-orders/`, новий) — 5 HTTP-методів, кожен покритий тестом:
  `getGroupInvite$` (ланцюг: існуючий `GuestInviteService.getInviteToken$` → токен → `getInvite$`),
  `getSessions$`, `getOwnerSessionId$`, `getStatus$`, `submit$` (POST, `Observable<SubmittedDish[]>`).
  Сервіси лишаються «чистим RxJS» — Observable, які легко мокати spy-ами; сигнали живуть лише на межі компонента.
- **Дані сторінки:** `getGroupInvite$(reservationId)` → `switchMap` (другий запит стартує з відповіді першого — інакше `undefined.GroupReservationId`) → `forkJoin({ sessions, status, owner })`;
  статичний `GROUP_ORDER_PREVIEW` замінений на сигнальні поля + `computed`-похідні (`participants`, `consolidated`, `total`, `unsubmittedCount`, `hasDishes`, `sentOut`).
- **«My Pre-Order»:** картка дістає `isMe` (порівняння сесії з `getOwnerSessionId$`).
- **Головна пастка — Grand Total $540, а не $760:** `consolidatePreOrder()` рахує лише підтверджені кошики (Olena «Still choosing» на 220 не входить). Сторінка чесно пояснює різницю жовтою плашкою «1 participant hasn't submitted their cart yet…».
- **Стани екрана:** завантаження винесено в метод `load()` (не одноразовий `ngOnInit`) — кнопка «Try again» перевантажує запит (`getGroupInvite$` викликається вдруге); `errorStatus` → 404
  «Group reservation not found»; `hasDishes()` → «Participants haven't added any dishes yet»;
  `loading`-сигнал на час запиту. Усі три стани перевірені тільки тестами: демо-перехоплювач на ці запити завжди відповідає успіхом, тож в браузері я їх не відтворювала і скрінів цих станів не маю.
- **Submit Pre-Order:** діалог — спільний `<app-modal>` проєкту (`shared/custom-components/modal/`). Подвійний клік закритий двома шарами: `[disabled]="submitting()"` (бачить користувач) + `if (this.submitting()) return` у методі (гарантія для сервера). Після успіху: `sent` → бейдж «Sent to Restaurant», кнопка зникає (read-only за `02-sent-to-restaurant.png`). При помилці submit скидається лише `submitting` — екран живий, кнопка знову активна.
- **Експеримент 2×2 із подвійним кліком:** перевірила захист (guard / disabled / обидва / жодного). Без обох шарів `submit$` викликався двічі; з будь-яким одним — рівно раз. Висновок: прапорець `submitting` — джерело істини, `disabled` і `if` — два незалежних виконавці.
- **Витік підписок:** обидва `subscribe` зібрані в `Subscription`-сінк, `ngOnDestroy` відписує все.
- **Моки:** демо-бекенд скидає стан після перезавантаження — Submit можна тиснути знову; другий submit без перезавантаження дає чесні 400 «Group reservation was submitted.» — як справжній бекенд.
- **Стилі бейджа:** «Collecting pre-orders» — (`$neutral-200`/`$neutral-600`),
  «Sent to Restaurant» — (`$orange-100`/`$orange-600`)

### Рівень 3 — реальний бекенд + фонова синхронізація (61 тест: 52 попередні + 3 сервіс.sync + 6 сторінка.sync)

- **Реальний бекенд:** `environment.development.ts` → `backendUrl` мого деплою (API Gateway, eu-north-1);
  реальна реєстрація (Cognito), реальні бронювання, гості заходять через `/join/…`.
- **Тихі запити:** другий параметр `getSessions$(id, { silent: true })` / `getStatus$(id, { silent: true })` —
  у запит летить `HttpContext` із `SKIP_ERROR_TOAST` (`src/app/auth/skip-error-toast.context.ts`),
  тож інтерцептор не показує тост на кожну невдалу фонову спробу.
- **`ownerHeaders()`:** ланцюг Owner-екрана йде через `/guest/`-ендпоінти, а інтерцептор проєкту НЕ чіпляє
  туди JWT (передбачено для гостьового токена) → на реальному API запити лишались анонімними → 401
  («під маскою» CORS-помилки в консолі). Додаю `Authorization: Bearer <idToken>`
  (`AuthenticationService.getTokens()`) явно в `getSessions$`/`getStatus$`. Тестам заголовки байдужі — 61/61 тримається.
- **Синхронізація:** `timer(15_000, 15_000)` + `exhaustMap` (поки попередній запит у польоті, новий тік
  не стартує) + `forkJoin` свіжих кошиків і статусу. `startSync()` — із guard: «Try again» не плодить другий
  таймер; зупинка після Submit і коли віддалений статус уже не `Open`; `ngOnDestroy` вбиває таймер тим самим
  `Subscription`-сінком, що й решту запитів.
- **Без лоадера на фоні:** `loading` у фонових шляхах не чіпається взагалі — вимога виконується
  стриманістю, а не кодом.
- **Помилка фону не з'їдає дані:** `error:` чіпає лише `refreshError` → картки лишаються на екрані,
  з'являється «Couldn't refresh. Showing data from …»; повноекранна помилка рівня 2 для цього не використовується.
- **«Updated at HH:mm:ss» + Refresh:** мітка ставиться після першого завантаження та після кожного тіка/Refresh;
  `syncNow()` — той самий запит, але за кліком.
- **Дрібний UI-полірунок:** рядок синхронізації (`.sync-bar`), кнопки діалогу через слот `modal-actions`
  (`dialog-btn--ghost` / `--primary`) — той самий дизайн-словник сторінки.
- **Двовіконний досвід (головна перевірка рівня):** Owner-вікно відкрите першим, гість в інкогніто
  підтверджує кошик — сторінка Owner оновлюється САМА за ≤15 с. До появи таймера стояла мертва до F5;
  саме це спостереження рівень 3 і виправляє. Стан «Couldn't refresh» відтворила офлайном у DevTools,
  помилкову гілку — реальним 400 «Guest limit exceeded» на переповненій групі.

## Баги, які зелені тести не піймали (два кейси)

1. **Іконка-смітник зламала чужий тест.** Додавання `<img>` з `trash.svg` перед фото страви червоним зробило тест «фото страви має розмір 40×40» — він бере перший `<img>` у картці. Тест урятував ситуацію; виправлено без правки тесту — іконка стала декоративним
   `<span>` із CSS mask (дата: 41/52 → 42/52 GREEN).

2. **Тест перевіряє одне — браузер бачить решту.** Для жовтої плашки AI запропонував
   «елегантний» тернарник-склейку `hasn{{ … ? "'" : "'ve" }}t`. На 1 учаснику виходить коректне «hasn't» (саме цей випадок фіксує тест — він зелений), а на 2+ — нісенітниця
   **«hasn'vet»**. Усі тести лишалися зеленими; баг помічено очима в браузері на демо
   з двома непідтвердженими учасниками. Виправлено на читабельне `{{ n === 1 ? "hasn't" : "haven't" }}`. Висновок: тести гарантують лише те, що перевіряють, — решту має бачити людина.

## Баги, знайдені на інтеграції (код не мій — Initial commit)

1. **500, переодягнений у CORS.** `GET /reservations/{id}/feedback` падає в base-обробнику(немає `try/catch`, сервіс припускає, що замовлення вже існує) → 500 генерує сам API Gateway, а не код → у відповіді немає CORS-заголовків → браузер бреше «blocked by CORS», Angular бачитьstatus 0. Справжній статус видно лише на вкладці Network. Першими цим шляхом пройшли мої бронювання без pre-order (`hasSubmittedPreOrder: false`).

2. **Кнопка «Make a Pre-Order» губить параметри.** У діалозі після бронювання це
   `router.navigate(['/menu'])` без `preOrder=true&reservationId=…`; меню без параметрів не показує кнопок додавання страви, і перезавантаження не лікує — параметри в URL і є стан. Обхід: «Pre-order» з картки бронювання, яка будує повний query. Фікс — скопіювати `queryParams` з картки плюс регресійний тест; окремою зміною після здачі, щоб не мішати у коміт домашки.

3. **Одне бронювання — три різні підписи на трьох екранах.** У Owner-кошику «Table cf9e7fc1-dd82…» (UUID), бо `GET /reservations` не несе `tableName`, а фолбек друкуює сирий `tableId`; гість бачить охайне «Table 2» (бекенд додає назву в інвайт-відповідь); десь час з секундами, десь без; «for a reservation» проти «for the reservation». Причина: рядок збирають незалежно три місця, спільного формату немає, попри наявний у проєкті `date-helpers.ts`.

4. **Ліміт гостей перевіряється на читанні.** Бекенд віддає 400 `GuestLimitExceeded` на `GET /guest/invites/{token}` — тобто переповнену групу не може прочитати навіть Owner. Перевірка належить на створення сесії (`POST /guest/sessions`), а не на перегляд.

**Урок.** Після наповнення таблиць у консолі з'явилися нові помилки — це не зламаний код, це нові
запити до старих дірок: порожня таблиця = тиха консоль. Питання «яких даних тут не було раніше»
діагнозує швидше, ніж «що я змінила в коді».

`id`, `locationId`, `capacity`, `tableNumber`; фізична назва таблиці ін'єктиться через змінну оточення
`tablesTable`; GSI `locationId-tableNumber-index` заповнюється автоматично при записах у базову таблицю)
та `Services/Tables/TableService.cs` (графік роботи захардкоджений — закриття о 22:00 UTC, мінімальний
слот 90 хвилин, тому в елементах даних немає годин; доступність рахується виключно з таблиці Reservations).

**Зміни:**

- Створила seed-файли у форматі payload для `aws dynamodb batch-write-item` і завантажила в деплой
  eu-north-1: `locations.json` (3 локації), `dishes.json`, `tables.json` (9 столиків — по 3 на локацію, місткість 2/4/6).
- Виправила «No waiters found»: потік бронювання автоматично призначає найменш зайвого офіціанта через GSI-запит до таблиці `Waiters` за `locationId`. Зареєструвала реального користувача в Cognito user pool
  і додала його як офіціанта для однієї локації (`aws cognito-idp list-users` → `sub` → `aws dynamodb put-item`); для двох інших локацій додала службові записи офіціантів (випадкові UUID як `userId`).

**Перевірка.** `aws dynamodb scan` підтвердив наявність записів; `GET /available-tables` повертає столики для кожної локації; `POST /reservations` тепер успішний на всіх трьох локаціях (раніше падав із помилкою про офіціантів).

**Використання AI.** Так — AI CLI-агент використовувався для читання коду бекенду, виведення точної схеми елементів, генерації seed-JSON і команд AWS CLI та тлумачення помилок. Усі команди переглянуті й виконані вручну у власному AWS-акаунті; результат перевірено через API-відповіді та інтерфейс застосунку.

**Зауваження на майбутнє.** `imageUrl` у seed-даних посилаються на S3-бакет попереднього середовища(старий акаунт / us-west-2) → зображення дають 404 (Chrome малює це як `net::ERR_BLOCKED_BY_ORB` — читав XML-помилку як «не картинку»); seed-файли зберігаються в корені `backend/restaurant-backend-app/`, щоб свіжий деплой можна було відтворити командою завантаження.
